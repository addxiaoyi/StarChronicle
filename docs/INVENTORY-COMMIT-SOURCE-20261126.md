# 库存提交回包丢失：源码与恢复验证

2026-11-26，继续两库 `codex/plugin-all-stages-20261125`。普通库存增减此前在保存异常后直接恢复旧内存；若数据库已经提交，下一次保存可能覆盖真实库存。带编号交易还会删除已经提交的回执，使同编号重试可能重复扣发。本轮沿用用户选择，只做源码、单元／数据库和打包服务验证，没有启动 Minecraft。

## 结果与接口边界

普通 `ResourceService.grant/consume` 在异常后重读同一存储域的库存、交易回执、工厂和活动批次，并执行现有生产／交付日志及完成归档校验。先撤销本次未确认的内存修改，再用持久状态恢复，恢复之后不再执行旧值回滚。SQL 首次归档迁移也可能已经提交，恢复会重新识别 V3、保留完整归档，仅让活动批次留在运行时。

普通接口没有稳定操作编号，保存异常仍返回 `false` 表示未正常确认，不能当作数据库必定未变更，不能据此安全自动重试。`NationResourceTransactionService.grant/consume(TransactionRequest)` 可以通过原编号、国家、资源、操作和分类匹配的持久回执确认 `ALREADY_APPLIED`；重复请求和重启后仍只执行一次。保存前失败并成功恢复旧状态时继续返回 `REJECTED`。描述文字的匹配规则维持原 API，不增加状态枚举。

无法读取、域变化或工厂／生产日志校验失败时关闭资源权威。所有库存入口在修改内存之前拒绝写入；即使存储随后恢复可读，该模块也必须正常重启、重新校验后才能恢复。`transactionReceipt` 与写入共用同步边界，读取等待提交及异常对账完成；权威不可用时抛错，不能把未知状态报告为“回执不存在”。`REJECTED` 在无法对账时不证明交易未提交，调用者须保留原编号。纯内存服务仍可使用，不承诺持久性。

科研支付捕获资源回执读取不可用，保留原支付／扣款／退款编号并返回 `RETRYABLE_FAILURE`，避免启动恢复因无法查询资源权威而中断。错误边界只包裹回执读取，不把其他运行错误全部吞掉。读取失败时不猜测扣款、退款状态；恢复后核对原凭据再继续。无资源费用的科研不查询资源权威。

## 故障复现与回归

新增测试直接使用生产 `PersistenceService` 的原子文件替换和真实 SQLite/H2。注入位置分别为替换／COMMIT 之前、成功之后抛异常、成功之后抛异常且后续读取失败。SQL 测试从冻结的真实 V1 工厂快照开始，同时验证归档升级、原工厂凭据和库存；包括旧状态回滚、同键重试、后续无关库存保存、重启及新国家首次入库。

旧代码首轮 42 项中 **29 failures、0 errors**，原日志、XML 和当时测试类字节保留。其后补充存储域初始化与并发读取，最终新增 **50 项**；专项连同普通库存、即时生产及科研资源支付共 **74 项通过**。保存期间的并发读取覆盖正常成功、保存前失败和提交后回包丢失。

第一版完整资源域 400 项加原有科研支付 7 项共 **407 项通过**。接着补齐科研调用方对“回执不可读”的处理，增加 6 项测试：在退款检查、扣款重建、国库扣款之后、退款扣款查询及退款回执查询五个位置中断，恢复后不重复扣款／退款；另验证只支付国库的科研不访问资源服务。
