# 工厂恢复回执校验与容量检查点

从 Chronicle `272b19b` 与 StarCore `2898143` 继续，仍使用两库 `codex/plugin-all-stages-20261125` 及草稿 PR #2／#3。按用户选择推进源码、单元测试和隔离 JVM，不启动 Minecraft。

## 实际改动

此前每恢复一条工厂批次都会调用单条回执查询：文件模式重新读入整个资源文件、校验全部生产日志，再查对应编号；SQL 模式逐条连接并重复检查整个日志的连续性。历史批次越多，重复工作越多。

现在工厂批次先完成身份、数量、占用、时间和快照指纹校验，再统一核对回执。文件模式在已经载入的同一份快照中遍历一次生产日志，同时核对全部已完成与活动批次。SQL 模式在一个 SERIALIZABLE 事务内确认快照与当前日志头相同、序号连续，再按最多 256 个操作编号分批读取回执。

已完成批次必须有内容完全相同的回执，活动批次不得有完成回执；缺失、篡改、重复、提前完成、不同存储域或过期 SQL 快照均拒绝恢复。文件的无关生产记录仍受完整日志校验。所有批次、原序号和重试键保留，存储格式未改变，没有跨事务或重启缓存。资源模块其他加载检查仍执行，此改动专门消除批次回执核对中的重复读取。

## 恢复容量对照

`tools/run-factory-recovery-capacity.py` 使用旧 JAR 编码同一份确定性样本：**1,000 个已完成批次、1 个活动批次、1,000 个生产回执**。每个探针串行运行，使用 `-Xmx64m`，文件模式实际从磁盘读取 Properties，SQL 模式使用真实 SQLite；完成与活动批次逐个核对全部字段，原库存数量保持一致。

这里测量的是存储读取、快照解码和批次回执校验，包含该路径类初始化；不是完整 ResourceModule／Minecraft 启动时间。每行是一次独立 JVM 直接测量，不是百分位统计：

| --- | ---: | ---: |
| 旧构件／文件 | 51.969 秒 | 1002 |
| 当前／文件首次 | 0.501 秒 | 1 |
| 当前／文件重启 | 0.475 秒 | 1 |

六轮均通过 Python 独立核验：文件字节哈希未变，SQLite 的 **4 张原表**逐行摘要未变，1,000 条生产回执保留且数据库完整。结果位于 `run/factory-recovery-capacity-20261126-1`。64 MiB 是 Java 堆，原生进程内存另计；共享机器耗时不构成生产承诺。
