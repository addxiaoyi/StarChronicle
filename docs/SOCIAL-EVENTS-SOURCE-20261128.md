## 实际行为

两种公开构造器现在只建立对象，持久恢复后显式调用 `start()`。实际 `SocialSimulationModule` 已按该顺序接入；外部调用者如依赖旧构造器自动启动，必须补上显式 start。公开 JVM 签名保持，不把二进制兼容检查当成行为完全不变。

周期改用 Paper／Folia AsyncScheduler，每小时一次，重复 start 幂等；注册失败可重试，停用时迟到的句柄取消。任务与名称采样后的异步续接绑定启用代次；停用取消已登记的任务并使旧回调失效，再启用后旧工作不能激活新事件。名称回原玩家 owner 采样，数据库操作回异步任务，消息分别回捕获的原玩家；重连不会接收旧通知。单个取消失败仍继续其他清理。

节日、冲突、名人和趋势统一先提交 SQL 再更新内存，过期删除成功后才移除状态和发送结束通知。查询即时排除过期事件，恢复本身不清理旧行。修正光棍节配置键不一致；事件 ID 使用 UUID 避免同毫秒碰撞，节日保留原稳定 ID。服务未指定数据库或数据库配置明确 disabled 时使用内存模式；配置了数据库但不可用、恢复失败或提交结果不确定时不会静默转为内存运行。

## 原数据与失败处理

继续使用 `starcore_social_events` 原表和原列，不改写旧行。读完整候选后再发布，非法枚举、非整数／溢出时间、重复 ID、坏 JSON、重复或未知效果字段及非有限值拒绝加载；旧空 effects 依原 codec 解释为中性值。SQL 异常保留证据，服务隔离后续读写，需重建服务并恢复权威状态。

事件写入和删除在 SERIALIZABLE 事务中重新核对加载过的完整行快照；MySQL 使用锁定读，SQLite 使用自身事务冲突检测。陈旧实例不能删除或覆盖其他实例已经提交的事件。写入、删除、commit 或连接关闭失败均按结果不确定处理，内存不发布，后续不盲目重放；测试包含实际提交后注入确认丢失，再由新实例读取已提交行。

通知没有持久 outbox，SQL 和玩家消息不是共同事务；提交后停用或断电可能不发送通知，不承诺端到端严格一次。已经取得提交锁的事务可先结束，stop 会等待该段退出。每次变更核对完整事件行集合，连接／提交等待及长期容量没有实服负载验证；SQL statement 的超时不是整个生命周期的硬时间上限。
