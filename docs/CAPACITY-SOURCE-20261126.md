## 已实现

schema 8 新增成员派生索引和同事务触发器；索引回填逐条解析快照，不修改原证据。成员退出／加入与投影同时提交，写入失败一起回滚；缺少索引表或同步触发器时从正文重建，损坏快照会回滚整次修复。

旧选择迁移改为 SQLite 磁盘排序键，保留真实秒／纳秒顺序和相同时间的 Java UTF-16 ID 顺序。旧定义快照及规范关联改为逐条迁移，仍校验原始哈希、元数据及未知旧投票时间。临时表在成功或失败后清理，原表字节内容保持不变。

剧情列表改用游标分页，每次最多返回 100 个实例、检查 256 个候选；空页仍可有续页。详情按 ID 读取，并重新检查正文成员资格。旧完整查询接口保留完整语义。后台成员观察与实例补入分批读取 64 个快照，活动 ID 索引避免每批重新排序；权限采集只保留唯一权限字符串。无条件共享剧情仍验证来源存在，但不再计算整套无用历史事实。

新增只读容量巡检及 SQLite backup 工具。使用方法、API 和维护边界见 [CAPACITY.md](CAPACITY.md)。

## 实际容量验证

`tools/run-capacity-contract.py` 在串行 `-Xmx64m` JVM 中使用冻结 JAR。V2 库从原始 DDL 建立，V7 库由实际旧 JAR 建立，没有通过修改版本号伪装升级。每库包含 **15,000 实例、15,000 事件、11,250 DONE 回执、5,000 保留种子、26,250 选择**，两份定义；查询玩家拥有 15 个实例，另有 150 个可见共享实例。

旧 schema 7 构件 `71d98cd5…623a6` 在同一 V2 fixture、同一堆限制下实际发生 `OutOfMemoryError`。独立核验失败进程退出后的原始表摘要未变。最终构件完成两库升级和再次启动，逐表核验 V2 的全部 9 张原表及 V7 的全部 40 张原表，原记录、JSON、时间、回执与定义哈希均保持一致；成员投影完整，旧选择顺序、外键及完整性检查通过。

最终实测目录 `run/capacity-contract-20261126-2`：

SQLite 查询计划确认成员查询使用 `member_instances`，后台批次使用 `instance_active_id`，没有重复全活动集合排序。每次列表取 17 条，九页完整读取 150 条且无重复。最终数据库分别为 220,766,208 和 252,252,160 字节。

前一容量构件 `9cc82595…d35c7` 也通过相同迁移，但 V2 首页 p95 为 224.781 毫秒。该实测暴露无条件剧情仍计算历史事实及后台批次排序成本，随后才加入上述优化；原结果和冻结指纹保留，未改写成绩。

这些耗时是共享机器上的当次直接引擎查询，不含 Bukkit 身份采集、触发恢复、复杂历史条件或多玩家并发。64 MiB 是 JVM 堆限制，进程原生内存另计；本报告不是生产容量或延迟承诺。
