## 改动与数据边界

以前每次 `RuleEngine.reload` 都多次构造包含全部历史定义的目录，并由运行时长期持有整份目录。现在加载时逐条校验全部证据，只保留当前剧情自身与条件直接引用的精确旧版本。所有 `all`／`any`／`not` 分支与节点选择条件均参与引用收集；退休定义自身的旧依赖不再展开，它们仍只是读取端点。

归档阶段只保留本次待归档的版本，继续复用语义等价 V1 证据。归档写入后再次逐条验证全库，成功提交后才在原存储锁内发布当前启用定义与配方。不相关旧图不会留在运行时；活动实例与待触发定义的固定快照仍由原持久化路径读取。

未引用的原始哈希、规范格式或 V1→V2 关联损坏仍使校验／加载失败。写后复核也会发现触发器修改其他旧证据，回滚新归档并保留旧运行时。选中版本的冲突变体继续拒绝引用；无关冲突仍完整保留在数据库。

公开 `DefinitionCatalog.read`、完整 `entries/evidenceEntries` 与 `StoryRuntime` 保持兼容语义。没有改变 schema 8、改写历史定义、删除去重凭据或引入跨事务缓存。

## 6,000 版本对照

`tools/run-definition-capacity.py` 使用冻结 JAR 和共同探针。旧 JAR 创建真实 schema 8 SQLite 夹具，逐条编码并保存 6,000 个历史版本，每个四节点、每节点 4,096 字符；其中 1,200 个 V1 和 4,800 个 V2，V1 升级关联由原迁移 API 生成。再加入当前定义和固定活动实例，共 6,001 行定义、6,001 行格式和 1,200 行升级关联，数据库为 **128,212,992 字节**。

先用十个旧版本确认旧构件和共同探针可完成加载、校验、重载与页面查询。随后复制相同大库，在串行独立 `-Xmx64m` 进程中比较。旧构件在加载完整目录时实际抛出 `java.lang.OutOfMemoryError: Java heap space`，失败日志保留。它不算当前构件通过，也不将一般启动错误当作容量对照。

| 当前构件进程 | 引擎加载 | 纯校验 | 同配置重载 | 引擎存活时 GC 后堆占用 |
| --- | ---: | ---: | ---: | ---: |
| 首次 | 15.039 s | 4.950 s | 15.022 s | 4,465,400 B |
| 再次启动 | 15.124 s | 4.977 s | 15.354 s | 4,464,368 B |

两次均只保留当前版本和直接引用的两个退休版本，V1/V2 读取内容相同；既有活动剧情保持可见与未完成。Python 独立逐表核验：旧构件失败、当前首次与重启后，**41 张原表的行数与逐行 SHA-256 全部不变**，schema 8、SQLite 完整性和外键检查通过。

完整校验仍多次扫描全部归档，以上时间明确显示其 CPU／磁盘成本。64 MiB 是堆上限，原生进程内存另计；GC 后读数不是峰值或生产服容量建议。公开完整目录、大量当前剧情、单一被引用版本的大量冲突变体和单条定义自身仍需要相应内存。
