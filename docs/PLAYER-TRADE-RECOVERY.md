# 玩家直售恢复与来源合同

本增量把原生 `/trade offer`／`accept` 的玩家钱包付款、国家库存交付改为持久分步协议。买方发出请求，卖方接受；买方支付货款、手续费与进口国关税，卖方收到完整货款。资源来自卖方国家库存，交付到买方国家库存，不是个人背包。市场订单簿、快捷买卖与贸易协定继续使用各自原协议。

## 冻结报价与权限

报价保存完整请求ID、双方玩家与国家、资源／国库权威域、钱包提供者身份与版本、资源数量、精确单价、已舍入货款、费用及有效期。单价允许小数，货款按HALF_UP保留两位；手续费和关税以整数分保存。报价后的税率变化不能改变已冻结金额。每位买方最多64个未终结请求，列表展示最近128条，完整ID仍可查询旧记录。

关税服务在创建报价时解析，允许税收模块晚于资源模块注册。跨国报价若当时缺少税收服务会拒绝继续，不会按零关税保存。

创建和接受前都核验双方当前国家成员身份及`resource.trade`权限。只有原卖方能接受或继续；原参与者可在离国或国家交接后查询原交易。已接受的义务不因报价随后到期而删除；已完成的重放也仍核验原卖方，继任创始人不能冒用其请求。

`/trade status <完整ID>`只查询。`/trade resume <完整ID>`仅从已证明安全的下一步继续；不会因等待时间经过而判断付款成功或失败。命令与GUI在创建结果不明时仍显示原ID，便于核对。资产写入限定Paper主线程，Folia保持拒绝写入。

后续审计增量提供`/trade audit <完整ID>`与原参与者API，返回经过SQL日志验证的完整步骤和冻结钱包操作；查询不调用钱包或推进状态。详见[只读审计合同](PLAYER-TRADE-AUDIT.md)。该能力没有解除Vault永久UNKNOWN的限制。

## 持久状态与资产

正常路径为`OFFERED → RESERVED → DEBIT_INTENT → DEBIT_ACKNOWLEDGED → CREDIT_INTENT → CREDIT_ACKNOWLEDGED → SETTLED → PROJECTED`。

1. `RESERVED`与卖方库存扣减共同SQL提交，资源留在持久报价所表示的托管义务中。
2. 调用钱包前先提交对应INTENT。只有本次成功保存新INTENT的执行者可以调用一次原提供者；第二实例或重启恢复不能重复调用现存INTENT。
3. 钱包响应另行保存。提供者明确拒绝扣款可返还库存；明确拒绝卖方收款可尝试一次买方退款。已确认退款后才能返还库存。
4. 两次付款均获确认后，买方库存增加、原生国库费用入账、精确税款回执与`SETTLED`在同一个SQL事务提交。没有单独写入SETTLED的旁路。
5. `SETTLED`作为历史／商业记录的持久待办；按稳定ID补写不可变来源记录，全部成功后推进`PROJECTED`。重复保存不能覆盖后来修改的历史状态。

调用结果为空、抛异常、报告金额不一致，或者调用后无法保存响应，都会停在UNKNOWN或未完成INTENT。失败响应若同时报告非零／无效金额，也视为不确定。退款被拒或不确定同样需要人工核对。本版没有管理员手工强制成交、推测性退款或解除UNKNOWN的命令。

Vault的SUCCESS仅表示提供者确认本次调用。它没有持久幂等键、可独立查询的付款回执，也不与原生SQL共同提交。正常重启和当前Essentials文件余额可以证明本次测试的恢复结果，不能据此承诺外部付款与资源的端到端严格一次或物理断电原子性。

## 日志与旧数据

`starcore_player_trade_head`和`starcore_player_trade_events`保存独立权威域、单调步骤序列、每笔版本、规范JSON与累计摘要。读取时检查整个已提交前缀、状态转移和冻结条款；删除完整尾记录也不能伪装成较短合法历史。所有已结算手续费／关税必须能在原生国库中找到身份、国家、金额、类型、说明与时间均一致的回执。

SQL提交前后确认丢失不在同一次调用内自动重读并重试钱包。库存先重核持久状态，后续由原卖方以原ID查询或继续。各模块使用同一DataSource和revision写入协调，陈旧实例不能覆盖新库存。

旧Fabric、RefundLedger、普通可变贸易历史不被升级成新协议的成交凭证。旧历史默认`buyer_funded=0`；新来源记录使用`buyer_funded=1`，卖方净收入等于货款，费用由买方另付。历史快照同时兼容旧format1和新format2。MySQL历史时间列迁移为至少毫秒精度；不能补回旧数据已经丢失的毫秒。

Chronicle通用贸易历史读取器兼容可选`buyerFunded()`能力。旧API缺少该方法或返回false时，事件内容保持原样；true时检查按分舍入的货款与卖方净收入，并标记`trade.tax_payer=BUYER`。该来源仍为`TRADE_HISTORY_RECORDED`／`NOT_PROVEN_BY_HISTORY_JOURNAL`，不会生成玩家成交贡献。方法异常或返回非布尔值时拒绝该页，不能当作旧API跳过。

原`TradeAcceptedEvent`保留为完成投影后的实时通知。通用事件总线仍是尽力交付，写入PROJECTED与通知之间发生中断可能失去通知；它不是季节奖励的持久投递证明。需要可靠消费的模块应读取新结算来源，不把该事件当作钱包持久回执。

## Chronicle持续消费与贡献

`PlayerTradeRecoveryService.settlementsAfter(domain, after, limit)`只返回连续的不可变SETTLED回执，序列独立于报价、调用意图、退款和历史投影步骤。Chronicle以`starcore.player-trade.settlements.v1`持久收件；检查域、连续性、原始主体、精确金额与规范事实后，将事件、贡献及收件确认共同提交。

每笔产生一条`PLAYER_TRADE_SETTLED`，签发者为`StarCore.PlayerTradeRecoveryService`。事实明确包含`NATIVE_DELIVERY_AND_TAXES`、`PROVIDER_ACKNOWLEDGED`和`NATIONAL_STOCKPILE`。它不是外部钱包持久付款证明。

卖方贡献单位为`trade.player-resource:<资源>`、金额为实际交付数量；买方单位为`trade.wallet-acknowledged`、金额为含费用的已确认付款。每方各有个人／原国家两个查询视图，共四条，均关联同一成交事件。操作ID区分SELLER／BUYER，因此同国交易也不会碰撞；这些视图不增加收益、奖励或成交次数。国家继任者可查询本国视图，原贡献操作者保持不变。

尚待单独推进：永久UNKNOWN的可信处置、外部钱包可查询幂等协议、市场撮合、旧钱包业务迁移、个人背包、长期容量、Paper实际调用中断与物理断电、完整Folia和生产部署。当前读取仍会核对全部日志，不能将分页接口存在等同于已完成大容量优化。
