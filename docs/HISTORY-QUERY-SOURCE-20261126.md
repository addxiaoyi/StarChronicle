## 改动与兼容

此前规则即使只引用普通身份事实，也会统计世界及当前国家／玩家的全部历史。现在规则条件与 NPC 事件反应使用 `HistoricalFacts.readRequested`，按条件实际引用的作用域和类型读取；普通条件不发历史计数 SQL。类型使用绑定参数，每批最多 256 个，包含点号、Unicode、空格或 SQL 样文本时仍是原始类型字面值。

新增 `history_type(type,id)` 覆盖索引，在打开现有 schema 8 库时补建，无版本提升、事件重写或历史缓存。计数仍读取调用方同一事务的真实事件与主体索引，未提交事件可见，回滚后不会留下缓存值。

旧 `history.TYPE` 缺失时仍不存在；明确作用域的缺失类型只在主体已知时返回零，未知玩家／空国家不会产生零。公开完整投影 `read` 和 NPC 对话视图保持完整结果，所以没有历史条件的对白仍可渲染 `{history.TYPE}` 占位符。规则继续读取固定定义全部条件分支所引用的类型，没有更改条件的三值逻辑或权限判定。

## 冻结构件对照

`tools/run-history-query-contract.py` 使用旧 JAR 建立真实 schema 8 样本，再复制给旧、新 JAR，各执行首次打开与新进程重启查询。每次查询 JVM 限制为 64 MiB 堆，串行运行。样本包含 **60,000 事件、602 种类型、各 60,000 玩家／国家索引行、6 份定义、24 个共享实例**。只有 RARE 类型被相关历史谓词引用：世界 121 条、当前玩家 61 条、当前国家 41 条。

真实 `RuleEngine.storyPage` 分页结果在新旧构件一致：已知国家看到 20 个实例，未知国家看到 8 个，完整遍历无重复。直接历史投影同时校验缺失旧别名与明确零值。Python 独立读取 SQLite 复算计数，逐表比较全部 **41 张原表**的行数和内容 SHA-256，并检查完整性、外键及 schema 版本；四轮全部通过。

查询计划确认世界计数定位 `history_type`；样本的玩家条件先定位相应类型，再以 `(event_id,player)` 精确检查参与关系，不再逐个读取该玩家的全部事件并排序。新索引使该数据库从 44,748,800 增长至 46,514,176 字节。首次打开／补索引约 0.919 秒，重启打开约 0.848 秒。

这里的时间是共享机器上的隔离引擎测量，不含 Bukkit 身份采集、网络、并发玩家或 NPC 完整展示。64 MiB 是 Java 堆限制，原生进程内存另计；不能据此承诺生产延迟或容量。
