# SQL 终态贸易归档

2026-11-26 源码检查点。批量回执恢复减少了重复读取，但此前每次库存保存仍编码全部贸易执行，定时恢复和列表查询也会复制终态历史。现在 SQL V2 活动账本仅驻留未结束执行，COMPLETED、REJECTED 和 REFUNDED 的完整记录进入 `starcore_resource_trade_archive`，保留原编号、冻结条款、审批、原配额窗口、路线和交付凭据。

首次业务保存将 V1 终态与活动账本、库存、配额、路线同事务迁移；迁移中途失败会整体回滚，原文件不改写。终态编号不能改回活动，冻结条款不能重写，V1 快照不能覆盖 V2。提交回包丢失后按原数据库恢复，原编号查询／重试返回原终态，不重复付款或交付。生产存储路由与故障包装层均已接入。

每条归档带字段摘要、连续序号和摘要链。恢复按最多 256 条分批验证完整归档、原交付回执，以及配额和路线引用；同一窗口的配额使用量同时计入活动和归档执行。点查与分页也验证所读行、相邻摘要链和原交付，发现冲突或不可读会隔离资源模块。分页按创建时间倒序和原执行编号排序合并两部分，保留原 API 与国家范围；编号排序使用 ASCII 对应的十六进制索引，避免数据库大小写排序改变结果。

## 冻结旧数据与新构件对照

旧 JAR 生成 2,000 笔完成执行、一个已交付 PAID 和一个等待确认记录，写真实文件并导入 SQLite。旧、新 JAR 用相同数据库在 96 MiB 堆下恢复、保存并重复保存 20 次。新构件再以 48 MiB 堆独立重启，验证深页和原编号查询。

| 构件与阶段 | 保存后驻留执行 | 活动快照属性行 | 首次保存秒数 | 20 次保存秒数 |
| --- | ---: | ---: | ---: | ---: |
| previous-first | 2002 | 40062 | 0.638 | 12.396 |
| current-first | 2 | 64 | 3.183 | 0.254 |
| current-restart | 2 | 64 | 0.099 | 0.296 |

Python 独立核对每条归档字段与旧 V1 字段完全相同，重算每条摘要和完整链，确认所有原编号保留；待批准和 PAID 字段保持，库存、原交付回执及其他原表摘要不变，旧文件字节不变，数据库 integrity_check 通过。工厂账本的空归档元数据按既有 V3 规则初始化。单次时间仅为本机观测，不是生产吞吐基准；首次 V1 迁移仍有全量装载与写入成本，堆外内存另计。

相同最终 JAR 还通过四 JVM 贸易／Chronicle 契约，覆盖国库提交后断线、交付提交后断线、恢复、原编号重放、唯一库存／资金／配额／路线结果与持久历史游标。验证器同时核验 V2 归档终态、摘要和头。三 JVM 工厂／Chronicle 回归也通过。未启动 Minecraft。

## 兼容与剩余范围

文件模式保持完整 V1，仍驻留终态。SQL V2 必须备份完整资源数据库，包括活动表、归档表、交付回执和已有工厂等表；单独 Properties 不能恢复 V2，旧 JAR 不能写入 V2。不能删除归档或编号来控制增长。

活动执行、国库凭据、旧文件来源、首次迁移峰值和归档完整扫描仍有长期成本。深页 OFFSET 和归档数量核对不保证恒定耗时。多实例线性一致、长期在线负载、MySQL、当前 Minecraft／全栈 Folia 和第三方实际组合仍待验；十阶段目标继续进行，按用户要求先做源码和单元测试。
