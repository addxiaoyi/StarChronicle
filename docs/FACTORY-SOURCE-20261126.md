## 实现范围

StarCore 定时工厂新增稳定批次编号 API 和 `start/collect/status` 命令。命令与服务核验当前国家创始人。开始时把精确投入扣除、工厂占用、冻结配方数量和到期时间放入同一持久快照／SQL 事务；完成时把固定产出、工厂释放、批次完成状态与 `ProductionReceipt` 同事务提交。升级、停用、配方修改或删除不会改变已有批次；重复请求不重复扣料或发料。旧批次编号不会收取工厂的新一轮。

批次持久保存原国家、工厂和开始操作者。继任创始人可以收取，但不能取代原贡献者；无玩家身份的系统批次只生成国家生产历史。定时完成进入现有生产来源，使用保留前缀 `factory:`，即时加工入口不能占用或重放该命名空间。Chronicle 无须增加另一种观察事件：开始不入生产历史，完成回执仍由已有游标、历史与贡献事务接收。

原生工厂状态移入资源模块的统一事务锁，公开查询返回副本；建造、升级和运营变更同步保存。兼容旧 `startProcessing/completeProcessing`，但不确定结果抛异常并带出原批次编号，新集成应使用显式编号 API。保存不确定时重读库存、批次、工厂和日志；重读失败暂停后续保存，防止旧内存覆盖可能已提交的状态。库存读取也等待该事务锁。

新格式保留全部批次编号、活动绑定、数量和完整性指纹，重启检查完成回执与状态一致性。坏工厂、缺失记录或混用文件／SQL 状态不会静默丢弃。首次迁移修复了交付日志先写存储域、使 SQL 被误判非空而漏迁完整快照的问题；初始资源状态、工厂、批次、两类日志和迁移标记同事务保存。失败全部回滚。

旧活动批次没有冻结配方与实际扣料证明时，保留原记录并返回 `LEGACY_REVIEW_REQUIRED`。不会用当前配方自动发料、退料、生成回执或贡献。此检查点没有新建玩家建厂收费规则，也没有自动认领或丢弃旧批次的管理入口。详细协议位于配套 StarCore `docs/TIMED-FACTORIES.md`。

## 保留失败与边界

首轮 83 项中有 1 失败和 2 错误。失败来自溢出测试未检查大额 grant 被现有安全上限拒绝；已改成三次允许的入库并断言真实库存。两项错误分别在 SQLite/H2 复现上述实际迁移缺陷，修复后新增整次迁移回滚用例。后续 87 项通过，但该次 verify 的格式检查遇到并行补充的源码修改而失败；最终检查使用冻结源码，早先日志与 XML 独立保留。

本轮没有当前 JaCoCo、原生全量、真实玩家或 Minecraft 生命周期验收。Chronicle 主源码和插件构件仍为容量检查点的 933 项通过版本，本轮通过实际构件契约验证新原生完成来源。工厂历史当前保存在完整快照中，重启和保存成本随历史增长；长期容量、旧批次人工核对策略、全栈 Folia、第三方组合与当前构件实服仍需继续。十阶段目标保持进行中。
