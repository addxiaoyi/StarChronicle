# 贸易与库存的锁顺序

2026-11-26，续接贸易快照恢复检查点。原生库存的同步保存先持有 ResourceModule 监视器，再调用同步的贸易快照；执行协议则先持有 SimpleResourceTradeService 监视器，再读取／消费资源。两条路径存在相反的加锁顺序，同时执行时可能相互等待。

修复让依赖原生 ResourceModule 的贸易服务共享资源模块的监视器；使用其他 ResourceService 的服务实例继续使用自身监视器。22 个业务入口和 8 个快照／恢复入口统一进入这把锁，移除原有相反顺序的同步方法。可用状态在取得锁后检查，已排队的查询不能在库存提交过程中返回过时的禁运／配额结果；提交失败并隔离后，它会抛出不可用错误。

此锁覆盖服务管理的操作与库存保存之间的协调，不替代持久事务。贸易仍调用原有国库／库存接口，未新增跨服务原子提交或稳定执行编号；普通布尔库存接口遇到提交结果不确定时仍不能据 false 自动补偿重试。原生国库转账路径没有反向资源调用；其他 ResourceService／TreasuryService 实现须自行遵守其并发合同。

公开返回的可变贸易模型与外部已持有引用仍是独立待办；不能把服务入口统一加锁表述成所有字段或所有第三方调用都获得线程安全。事件处理、长期吞吐、全栈 Folia 和实际插件组合也不由本轮源码检查认证。
