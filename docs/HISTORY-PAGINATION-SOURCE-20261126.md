# 历史游标分页：源码与深页验证

2026-11-26，继续 `codex/plugin-all-stages-20261125`。本轮按用户选择只做源码、单元／SQLite 与打包服务契约，未启动 Minecraft。**957 项完整 verify**、56 项专项和 12 万事件的新旧冻结 JAR 对照通过。

## 行为与兼容性

原历史列表每次翻页都用 OFFSET 跳过已读记录；原时间索引的 ID 排序方向也与查询不同。现在新增 `ChronicleService.historyPage(nationId,playerId,beforeEventId,size)`，返回不可变 `HistoryPage(events,nextCursor)`。首次传 null，后续使用返回的事件 ID；根据该事件在同一事务中的原始 `(time,id)` 查询后续记录，原时间字节和降序规则不变。

每次只解码当前页，额外查看一行判断是否还有后页；最后一页即使正好满页也返回 null 游标。游标不存在、超过事件 ID 长度限制或不属于当前国家／玩家过滤范围时明确拒绝。所有过滤都来自实际参与关系，交集仍是交集，游标不提供权限。

schema 8 打开时补建 `history_cursor(time DESC,id DESC)` 派生索引，不改写事件或提升 schema 版本。旧编号分页 API 保留；新增默认方法让旧第三方实现仍可加载，并明确报告不支持该可选能力。

历史 GUI 的顺序翻页使用游标，最近 128 个查询位置可直接回退；进入证据详情后返回原位置。显式编号跳页和超出保留范围的回退使用原 API，仍有 OFFSET 成本。页面不是固定时点快照：新到的较新事件在首页刷新后可见，迟到的较旧证据可能出现在后续页。

## 12 万事件对照

`tools/run-history-pagination.py` 用旧 JAR 生成相同 schema 8 夹具，120,000 条事件每八条共享一个时间，保存真实事件 JSON、哈希与参与关系。四个范围分别有 120,000／40,000／60,000／20,000 条匹配事件，每页 45 条，从约 75% 深度取得一页及下一页。旧构件使用编号分页，新构件使用前一条真实事件的游标；所有返回事件与独立 SQL 预期一致，无跨页重复。

每个进程各预热两次，再测量 25 次，以下为 p50，单位毫秒：

| 范围／页码（从 0 起） | 旧首次 | 旧重启 | 新首次 | 新重启 |
| --- | ---: | ---: | ---: | ---: |
| 世界／2,000 | 80.966 | 85.528 | 2.459 | 2.585 |
| 国家／666 | 113.687 | 116.220 | 1.256 | 1.176 |
| 个人／1,000 | 132.539 | 127.462 | 1.161 | 1.121 |
| 国家与个人交集／333 | 126.772 | 134.086 | 1.355 | 1.289 |

四个串行隔离 JVM 均使用 `-Xmx64m`，首次和重启均通过。Python 独立核对四个范围的匹配数、页码、游标和两页 ID；四次运行后 **41 张原表逐行摘要与行数保持不变**，schema、SQLite 完整性与外键检查通过。

原数据库为 91,222,016 字节，新增派生索引后为 96,911,360 字节。当前首次打开约 0.977 秒、重启约 0.655 秒。查询计划从顺序扫描与末项临时排序改为 `history_cursor ((time,id)<(?,?))` 范围定位。

这些是共享机器、有限分布样本的隔离引擎结果，不含玩家身份采集、服务器渲染、并发或网络。64 MiB 是 Java 堆上限，原生进程内存另计。稀疏国家／玩家范围仍可能扫描较多候选；旧编号跳页、实例／贡献等其他编号分页以及完整 NPC 历史投影仍有相应成本。
