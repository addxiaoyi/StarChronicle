# 贸易历史恢复读取与校验

2026-11-26 源码检查点。原生执行账本恢复曾为每个完成记录重新读取文件，或为每条 SQL 回执打开独立连接；记录越多，启动成本越高。此前仅在 COMPLETED 检查交付，PAID 的冲突回执及其他状态中不应出现的交付也需要拒绝。

现在文件校验遍历同一个已加载快照，不为每笔贸易重新打开文件。SQL 使用一个串行化读取事务，先比较原快照的权威域、执行版本、数量和摘要，再每批最多 256 个执行编号核对交付回执。每个完成记录必须匹配双方国家、资源、数量、类别、描述、域、序号和时间。合法 PAID 允许存在已提交但尚未保存完成状态的匹配回执；等待确认、PREPARED、待退款、拒绝和已退款状态出现交付则拒绝恢复。中间批次失败会回滚并关闭连接，不返回部分结果。生产存储路由和故障包装层均转发新的校验接口。

V1 格式保持，摘要按字段增量计算并保留原字符长度编码；规范校验每次只重新编码一行，不再创建整份账本的第二份 Properties 或整体摘要字符串。文件回执仍严格检查顺序、游标、重复编号和隐藏字段。执行账本及校验所用编号集合仍全量常驻，本轮没有删除终态或重试编号。

## 回归与冻结构件

1,440 项相关测试全部通过：1,243 项资源域、184 项国库及 GUI、13 项科研支付，零失败／错误／跳过。新增 49 项覆盖超过两批的读取、坏字段／缺失／提前交付、过期 SQL 快照、PAID 崩溃间隙、V1 摘要兼容、实际存储路由、后续批次读取异常的回滚／关闭与完整重试。旧主 classes 上最初 44 项中 29 failures 已保留，确认反例能捕获旧行为。

## 旧 V1 数据的实际恢复对照

旧 JAR 生成 1,000 笔 COMPLETED、一个已交付 PAID 和一个等待确认记录，先写真实文件并导入 SQLite。相同文件／数据库分别由冻结旧、新 JAR 在串行 64 MiB 堆 JVM 中恢复；新构件另启动独立进程复验重启。每阶段核对全部冻结记录及库存，Python 独立检查文件字节、数据库原表摘要和 integrity_check。没有启动 Minecraft。

相同最终 JAR 另通过四 JVM 贸易／Chronicle 契约，覆盖真实 SQLite 国库提交后断线、资源交付后断线、原编号续办、一次性配额／路线统计、历史游标和重放；同构件三 JVM 工厂／Chronicle 契约也通过。首次贸易契约的前两个进程通过，第三进程因 Windows 提交内存耗尽、无法提交 64 KiB metaspace 而退出，整轮保留为 FAILED。工具新增可配置堆上限后，用相同构件、48 MiB 堆在独立新目录完整重跑；原始失败日志和 JVM 错误报告均归档。
