# 工厂完成批次归档：源码与容量验证

2026-11-26，继续两库 `codex/plugin-all-stages-20261125`。本轮按用户选择推进源码、单元／数据库及打包服务契约，未启动 Minecraft。SQL 模式将全部完成凭据移入独立归档，运行时保留活动批次，按原编号读取旧结果；文件模式继续保存完整批次历史。

## 存储与行为

SQL 新保存使用 `resource.factory-runs.version=3`，状态表只保存活动批次、工厂绑定、完整性指纹及归档数量／摘要。`starcore_resource_factory_archive` 保留每条完成批次的原编号、存储域、工厂、国家、操作者、配方、批次数、投入、产出、开始／到期／完成时间和原生产序号，不删除来源、奖励或重试凭据。

归档以小写 SHA-256 编号键定位，原编号仍核对；另存连续归档序号、每行摘要与摘要链。归档序号独立于混合即时加工／定时生产的生产序号，不要求工厂回执占满整个生产日志。新记录、库存、活动工厂状态、生产回执与归档头在同一 SERIALIZABLE 事务提交；任一写入失败整次回滚。提交成功后才从运行时移除完成批次，回包丢失沿完整状态对账恢复。

`factoryRun`、开始重试和完成重试仍接受原编号，活动表未命中时按摘要键读取归档并核对原始生产回执。已完成结果不会再次发料，也不会收取工厂的新一轮。启动时按最多 256 条归档分页核对全部记录、摘要链、工厂／国家绑定和原完成回执，发现缺行、篡改、错误头或丢失来源时拒绝恢复；原活动批次仍不得提前出现生产回执。

## 迁移与备份

V1／V2 只读加载保持原格式。第一次业务保存将已有完成批次原子归档，保留活动批次；逐项核对旧快照，拒绝丢弃或修改既有证明。首次迁移仍需完整读取旧快照，内存和时间随旧历史增长，迁移完成后的常驻对象才只随活动批次增长。

V3 必须连同原生完整数据库备份：状态表、归档表、生产／交付回执及迁移信息缺一不可。不能把 V3 状态属性单独复制成文件存储，也不能只换回只支持 V1／V2 的旧 JAR。旧文件保留原值，不覆盖或假装变成新归档；已有文件到 SQL 的日志对账继续执行。

此项归档保留全部证据，仅改变完成批次的存放位置。原生库存／交易等其他快照集合、文件模式完整历史、首次迁移峰值、归档全扫描时间、SQL 计数和长期并发仍有独立容量边界。

## 实际回归与构件

首轮 98 项有 6 failures：旧故障注入只拦 V2 字段或完成属性，而新路径写入 V3 归档头；另一个旧测试将新 SQL 状态当成独立文件。保留原日志，改为拦截真实新事务写入点，并用真实旧文件继续验证文件／SQL 冲突。第二轮 120 项有 14 failures：新增测试错误预期 `grant` 抛异常，该 API 实际返回 `false` 并恢复库存；改为核对拒绝和库存不变。随后 346 项通过，补充非规范字段检查后的最终 350 项通过，未覆盖失败日志。

## 5,000 条完成凭据对照

`tools/run-factory-archive-capacity.py` 使用真实旧 JAR 生成 5,000 个完成批次和 1 个活动批次，复制相同 SQLite 库给新旧构件。生成进程上限 256 MiB；四个运行／重启进程串行，各 128 MiB。通过实际 `ResourceModule.grant` 首次增加 1 个库存单位并单列迁移，再做 20 次后续 grant。查询和重放首条、中间、末条旧编号，原活动批次保持未完成。

| 测量 | 旧 V2 | 新 V3 |
| --- | ---: | ---: |
| 运行时保留的批次对象数 | 5,001 | 1 |
| 状态表属性行数 | 65,041 | 43 |
| 独立完成归档行数 | 0 | 5,000 |
| 首次 grant（包含新构件迁移） | 677.783 ms | 5,149.900 ms |
| 后续 20 次 grant 的 p50 | 674.462 ms | 15.448 ms |
| 后续 grant 调用线程累计分配 | 1,272,826,984 B | 1,016,584 B |
| 新进程模块加载 | 2,296.866 ms | 1,367.577 ms |
| 新进程 GC 后存活堆 | 20,487,456 B | 11,719,880 B |

第一次运行中的 GC 存活堆分别为 15,777,760／15,721,184 B，几乎相同；库、线程和其他对象也参与进程内存，不能将批次对象数直接等同于总内存。分配计数只覆盖调用线程，SQL 保存在线程池执行的分配不在该指标内；累计分配不是峰值。耗时为共享机器的有限串行样本，不代表网络、持续并发或生产服延迟。

Python 独立复算 V3 输入指纹、归档逐行摘要及连续摘要链，合并活动与归档记录后逐项对比旧库的全部逻辑状态；仅允许预期 21 个库存单位变化。原 5,000 条生产回执、迁移标记和交付表的行数／逐行摘要不变。新进程重启和重放后两库各自全部表摘要保持不变，新库五张表包括完整归档。没有删除原完成凭据或制造新生产回执。
